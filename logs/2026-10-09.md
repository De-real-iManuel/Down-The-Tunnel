# What We Built

## HACK.Pay v0.1

HACK.Pay is a Python library that allows developers to gate FastAPI routes behind **HBAR micropayments using the x402 protocol**.

The intended developer experience is deliberately simple.

A developer can take a route like:

```python
@app.get("/api/data")
@paid("0.5 HBAR")
async def get_data(request: Request):
    return {"result": "paid content"}
```

and turn it into a pay-per-use endpoint.

The complexity of the payment flow happens underneath the decorator.

The basic flow is:

```text
Client
   │
   │ Request without payment
   ▼
HACK.Pay
   │
   │ 402 + PAYMENT-REQUIRED
   ▼
Client
   │
   │ Signs Hedera TransferTransaction
   │
   │ PAYMENT-SIGNATURE
   ▼
HACK.Pay
   │
   │ Verify
   ▼
Facilitator
   │
   │ Settle
   ▼
HACK.Pay
   │
   │ Payment-RESPONSE
   ▼
Route Handler
```

The developer using HACK.Pay doesn't need to manually implement that entire flow for every endpoint.

That is the point of the abstraction.

# What Was Implemented

### `@paid` decorator

The primary developer-facing interface.

It gates FastAPI routes and supports both synchronous and asynchronous route handlers.

### `PaymentGate`

The central orchestrator.

It coordinates:

**challenge → verification → settlement → idempotency → receipt publication**

### `HederaPaymentProvider`

The Hedera payment provider delegates payment verification and settlement to a facilitator over HTTP.

An important design decision:

**The server does not hold a private key.**

### `FacilitatorClient`

The HTTP client responsible for communicating with the facilitator endpoints:

* `/supported`
* `/verify`
* `/settle`

### `InMemoryIdempotencyStore`

Prevents duplicate settlement attempts.

The implementation uses per-key `asyncio` locks to protect concurrent requests.

### `NoopReceiptPublisher`

The default receipt sink.

It provides the receipt interface without requiring a durable backend yet.

The interface is designed so a durable implementation can be added later.

### x402 v2 Wire Types

The project now has Pydantic models for:

* `PaymentRequirements`
* `PaymentPayload`
* `SettlementResponse`

These models handle the difference between Python naming conventions and the actual x402 wire protocol.

### `HederaProviderConfig`

Validated provider configuration with network-aware facilitator defaults.

### Testing

The implementation currently has:

**108 tests**

covering:

* Unit behavior
* Integration behavior
* Protocol correctness
* Security
* Concurrency

# What Broke — And Why That Was Valuable

The most valuable part of this milestone wasn't simply getting 108 tests to pass.

It was discovering where seemingly reasonable implementations were actually wrong.

## 1. The x402 Wire Protocol Does Not Care About Python Naming

One of the biggest bugs was the difference between internal Python names and protocol wire names.

Internally, it made sense to write:

```python
pay_to
max_deadline_seconds
```

But the x402 v2 wire protocol expects:

```text
payTo
maxTimeoutSeconds
```

The initial implementation serialized the Python field names.

The facilitator rejected them.

The fix was to explicitly define Pydantic aliases and ensure wire serialization uses them:

```python
pay_to: str = Field(..., alias="payTo")
```

and:

```python
model_config = ConfigDict(
    frozen=True,
    populate_by_name=True
)
```

When sending data over the wire:

```python
model_dump(by_alias=True)
```

### Lesson

**Internal representations and protocol representations are not necessarily the same thing.**

A model can be perfectly valid Python and still be an invalid protocol message.

This is one of the most important lessons from this version.

---

# 2. A No-Op Implementation Still Has to Tell the Truth

The initial `NoopReceiptPublisher.is_available()` returned `True`.

But `publish()` discarded the receipt.

That created a dangerous situation:

If durable receipts were required, the system could believe receipts were available even though nothing was actually being stored.

The fix was simple:

```text
No-op publisher
      ↓
is_available() = False
```

### Lesson

A system should fail loudly when an important guarantee isn't actually available.

**False confidence is worse than an explicit failure.**

---

# 3. Network Defaults Can Become Financial Bugs

The provider configuration initially defaulted to the testnet facilitator regardless of the configured network.

That meant a mainnet configuration could accidentally resolve to a testnet facilitator.

That's not merely a configuration mistake.

In a payment system, that's potentially a serious operational problem.

The default facilitator now resolves according to the selected Hedera network.

### Lesson

**Configuration defaults are part of the security and correctness model.**

Never treat them as harmless convenience values when money or external state is involved.

---

# 4. Not Every HTTP Error Should Be Retried

The original facilitator error handling treated all `403` and `503` responses similarly.

That meant a transient `503 Service Unavailable` could fail immediately instead of being retried.

The implementation now distinguishes:

```text
503
 ↓
FacilitatorUnavailableError
 ↓
Retry
```

from:

```text
403
 ↓
FacilitatorInvalidResponseError
 ↓
Do not retry
```

### Lesson

Retry logic needs to understand **why** something failed.

A temporary infrastructure failure and an invalid request are not the same failure.

---

# 5. Logs Can Leak More Than You Think

The environment loader was initially logging the complete facilitator URL.

That could become a credential leak if sensitive information ever appeared in the URL.

The implementation now parses the URL and logs only:

```text
scheme://netloc
```

rather than the complete value.

### Lesson

Observability is part of security.

Logs are data.

Anything that enters a log should be treated as potentially persistent and accessible by people or systems that don't need the original secret.

---

# 6. FastAPI Supports Both Sync and Async

Another implementation issue appeared around route handlers.

Simply doing:

```python
await func(...)
```

doesn't work when the route handler is synchronous.

FastAPI supports both styles.

The payment layer now detects whether the handler is asynchronous and executes synchronous handlers through an executor.

### Lesson

Framework abstractions have contracts.

If you're building middleware on top of a framework, you need to understand the framework's supported execution models rather than assuming everything is async because your own code is.

---

# 7. Windows Encoding Taught Me an Unexpected Lesson

One of the stranger problems came from writing Python source files through PowerShell here-strings.

The files could receive a UTF-8 BOM:

```text
EF BB BF
```

and certain characters in documentation strings could become corrupted.

Ruff then refused to process the file correctly.

The safer approach is to write Python source files using a proper editor or explicit UTF-8 handling rather than relying on PowerShell string interpolation.

### Lesson

Development environments matter.

A bug doesn't always come from the application code.

Sometimes the tooling used to create the source file is the problem.

# CodeRabbit Taught Me Something Too

CodeRabbit introduced another lesson.

Its review state is associated with the commit it reviewed.

That means fixing the code doesn't automatically mean the old "Changes Requested" review disappears.

The repository can have:

```text
CI: GREEN
Code: FIXED
Review: OLD
```

and branch protection may still block the merge.

This made it clear that automated review systems themselves are part of the development workflow and need to be understood.

# CI

The project now has a nine-check CI matrix covering:

* Ruff linting
* Ruff formatting
* Strict mypy
* Unit tests across three Python versions
* Integration tests
* Security scanning
* Bandit
* pip-audit
* CodeQL

All checks are currently green.

One particularly useful discovery was `mypy --strict`.

It caught a mismatch around the renamed/aliased payment fields that could have become a runtime issue.

### Lesson

Different tools catch different classes of problems.

Tests tell me whether behavior works.

Type checking catches certain interface inconsistencies.

Linting catches code-quality problems.

Security scanners look for another class of risks.

Code review catches things automated tests may not.

The combination is much stronger than relying on any single tool.
